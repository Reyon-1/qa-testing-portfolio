# 场景设计与可复用做法

## 从接口条目到业务闭环

从三端接口文档建立覆盖矩阵，再按业务依赖组织场景。每一步既校验HTTP和业务code，也通过独立查询核对资源身份、状态和关联关系；响应契约另外验证类型及嵌套结构。

1. 本轮唯一标记初始化，独立会话登录。
2. 创建本轮资源，由列表精确名称及父对象定位ID。
3. 回读归属成功后开启后续写入/清理条件分支。
4. 编辑、启停、授权或业务流转，再独立查询保存结果。
5. 按依赖逆序删除，查询确认本轮ID不再出现。
6. 对原有资源取前后快照；允许保留的正常审计另行核对。

## 代表场景

| 场景 | 核心证据 | 业务边界 |
|---|---|---|
| 自建组织/用户额度 | 组织2→3、用户0.2→0.3→0.4逐次回读；超父级额度拒绝后原值不变 | 只改本轮对象，5条正常额度审计保留 |
| 跨端产品授权 | 管理端自建提供商/模型/产品；客户端依次核对ORG/USER/ALL授权范围 | 独立两端会话，发布投影有界轮询，清理两端依赖 |
| 真实文本调用 | 三种文本协议各1次，输出上限16；三笔按次消费各0.001，总额0.003 | 本轮用户/Key/产品；每轮最多3次生成，无生成请求重试 |
| 财务交叉对账 | 调用明细、账单明细、模型聚合、看板按相同期间核对 | 正确处理金额缺失、长ID及舍入边界，不把null变成0 |
| 文件导出 | XLSX结构、表头/行数或文件字节及摘要校验 | 有界只读下载；无删除入口的任务不随意创建 |
| ORG看板 | 独立ORG会话核对组织与用户归属；零消费组织统计一致 | TENANT账号403不直接定为故障，按角色准备测试资源 |

## 对可信结果的约束

- HTTP 200不代表业务成功。只有负向用例预期的拒绝才可通过，非预期403/500保留失败。
- 逆向请求返回错误并不自动等于通过，必须满足预先写明的业务码、提示、状态未变等断言。
- 原生响应Schema错误和脚本异常都必须处理；不靠禁用契约或移除断言获得通过。
- 轮询只用于验证码准备、产品投影、计费异步结果等有界等待；不悄悄重复真实推理请求。
- Runner报告含辅助验证码/分页请求，业务步骤与请求总数分别统计。
- 使用JUnit逐步骤校验顺序和实际执行数量，防止条件跳过步骤却把场景算作完成。

结构示例是执行快照的白名单投影，用于解释已实现流程，不是可导入的Apifox项目。业务路径已统一泛化。
