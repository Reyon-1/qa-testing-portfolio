AI 运营平台 KIMI K3 API 性能压测方案

文档日期：2026-09-11

当前状态：单轮正式方案已定稿，尚未启动模型调用和性能压测

测试环境：198.51.100.10

压测工具：Apache JMeter 5.6.3，Java 17

唯一测试模型：KIMI K3(压测)

API 请求中必须使用的精确模型值：kimi-k3(压测)

1. 测试结论先行

本次不通过浏览器反复操作“模型体验”页面发压，而是使用 JMeter 直接调用平台对外提供的 OpenAI 兼容接口：

http
POST http://198.51.100.10/v1/chat/completions

该方式会真实经过以下完整链路：

text
JMeter
  -> AI 运营平台API网关
  -> API Key鉴权
  -> 模型权限、额度和限流校验
  -> 固定模型路由
  -> KIMI K3(压测)对应供应商
  -> 大模型推理
  -> 平台响应处理
  -> 用量、计费和调用日志记录
  -> JMeter

因此它最适合同时评估：

  1. AI 运营平台的API网关、鉴权、路由、连接池、日志和计费链路负载。
  2. KIMI K3(压测)背后供应商的并发承载、排队、限流和推理性能。
  3. 整条端到端链路在最高400并发线程下的可用性、吞吐量和响应时间。

本方案禁止使用以下模型：

  • 自动路由
  • deepseek-v4-pro-qinwenxiu
  • 任何其他模型

原因：自动路由可能把请求分配至不同供应商，无法准确评估KIMI K3供应商负载；其他模型不在本次任务范围内。

3. 测试目标

3.1 核心目标

  1. 获取1线程条件下的接口功能和性能基线。
  2. 验证25、50、100、200、400并发线程下端到端调用是否稳定。
  3. 确认各并发阶段的成功率、错误率、吞吐量、P90、P95、P99和最大响应时间。
  4. 找出响应时间明显增长、错误率开始上升或吞吐量不再增长的性能拐点。
  5. 确认首次出现429、平台5xx、供应商5xx、连接重置和读取超时的并发级别。
  6. 判断400并发下平台是否仍能完成API Key鉴权、固定模型路由、供应商调用、计费和日志落库。
  7. 结合服务端监控区分平台瓶颈与KIMI K3供应商瓶颈。
  8. 验证高压结束后，接口是否在合理时间内恢复到基线水平。

3.2 本次不测试

  • 登录接口和验证码性能。
  • 浏览器页面渲染性能。
  • 模型体验页面的前端交互性能。
  • 自动路由性能。
  • 其他模型或多模型混合流量。
  • 多轮上下文对话。
  • 图片、语音、视频和Embedding接口。
  • 供应商直连性能，除非后续由开发或运维提供供应商直连接口和测试Key。

4. 统一测试数据与请求口径

4.1 固定问题

所有正式请求统一使用：

text
给出一套成都旅游一日游方案，50字左右

不得随机替换问题，不得携带上一轮问答，也不得在同一个上下文中累计消息。

4.2 推荐正式请求

http
POST http://198.51.100.10/v1/chat/completions
Authorization: Bearer sk-REPLACE_WITH_YOUR_KEY
Content-Type: application/json
Accept: application/json

非流式请求Body：

json
{
  "model": "kimi-k3(压测)",
  "messages": [
    {
      "role": "user",
      "content": "给出一套成都旅游一日游方案，50字左右"
    }
  ],
  "temperature": 0.2,
  "max_tokens": 100,
  "stream": false
}

参数固定原则：

参数固定值目的
modelkimi-k3(压测)保证所有请求落到指定模型和供应商
temperature0.2降低随机性，使各阶段输出相对可比
max_tokens100控制最大输出规模，减少输出长度波动
stream首轮false便于JMeter准确完成JSON断言和总耗时统计

注意：自然语言中的“50字左右”不能严格控制输出Token数，所以必须同时固定max_tokens。正式压测前应以单请求确认100 Token不会把正常答案截断。如果目标模型不接受temperature或max_tokens，应以单请求返回为依据修改，但五个梯度阶段必须保持完全相同的Body。

4.3 会话隔离

对外OpenAI兼容接口的主请求不需要登录Token，也不使用平台页面的登录会话。每次请求只包含一个user消息，因此天然是独立单轮请求。

不得在每个JMeter线程内执行登录和验证码请求。否则测到的将是登录系统加模型API的混合性能，并会造成验证码大量刷新，污染结论。

5. 为什么主测试采用API Key直调

平台模型体验页面内部使用登录会话，并调用：

http
POST /api/v1/chat/completions
Accept: text/event-stream

模型体验页面适合验证页面功能，但不是本次负载测试主入口，原因如下：

  1. 页面调用会混入登录Token、页面逻辑、前端渲染和浏览器资源消耗。
  2. 400个浏览器会话会先压垮压测机，不能代表API服务真实容量。
  3. 用户实际要验证的是平台API Key调用链路。
  4. POST /v1/chat/completions能稳定固定model=kimi-k3(压测)。
  5. JMeter可以直接对API采集状态码、吞吐量、分位响应时间和错误类型。

6. 整体执行顺序

正式测试只执行一轮完整流程，不再安排第二轮扩大循环复测。该轮分为四部分，必须按顺序执行：

text
T0：环境和单请求预检
  -> T1：非流式五级折中梯度容量测试
  -> T2：流式三档代表性连接专项测试
  -> T3：恢复性验证

本轮正式压力请求总数为：

text
非流式29,500次 + 流式6,250次 = 35,750次

另有T0预检3次和T3恢复检查10次，因此整个执行流程预计产生35,763次模型调用。每个阶段必须使用独立Label、JTL和HTML报告，最终再汇总为同一份桌面Markdown测试报告。

任何阶段达到停止条件，都必须停止继续升压，先保存结果并排查。

7. T0：压测前预检

T0不是性能结论，只用于证明脚本和业务链路配置正确。

7.1 API Key和模型检查

请求：

http
GET http://198.51.100.10/v1/models

通过条件：

  • HTTP状态码为200。
  • 响应模型列表包含精确值kimi-k3(压测)。
  • 不出现401、403、429或额度不足错误。

7.2 单请求功能检查

配置：

text
线程数：1
Ramp-up：1秒
循环次数：3
stream：false

必须人工检查至少一次完整响应，确认：

  • HTTP 200。
  • 响应是JSON。
  • choices[0].message.content非空。
  • 回答内容与成都一日游有关。
  • 回答没有明显截断。
  • 如果响应包含usage，则total_tokens > 0。
  • 平台消费记录或调用日志能够查询到对应请求。

只有T0连续3次全部成功，才允许进入25线程阶段。

8. T1：非流式五级梯度容量测试

8.1 推荐梯度

阶段并发线程每线程循环预计请求总数Ramp-up阶段间休息
P1252050030秒3分钟
P250201,00060秒3分钟
P3100202,000120秒3至5分钟
P4200306,000180秒5分钟
P54005020,000300秒5分钟后进入流式专项

正式五档共计：

text
500 + 1,000 + 2,000 + 6,000 + 20,000 = 29,500次模型请求

首轮不使用每线程500次。若按五档均循环500次，总调用量会达到几十万次，测试时长、供应商消耗和日志量过大，也不利于快速发现拐点。

8.2 为什么采用20、20、20、30、50次折中循环

  • 25至100线程使用20次循环，兼顾样本量和低压阶段执行时间。
  • 200线程提高到30次循环，获得6,000个中高压样本。
  • 400线程提高到50次循环，获得20,000个最高压样本，用一轮同时观察容量和持续稳定性。
  • 正式JTL不保存完整回答，所以样本量增加后主要增加测试时长和服务端负载，不应显著扩大JMeter内存占用。
  • 本轮结束后不再安排相同梯度的第二轮50循环复测。

循环次数主要影响持续时间和样本数；线程数才直接决定瞬时并发压力。因此不能把“本机能开400线程”理解为“每个线程必须循环500次”。

正式执行前已重新核实本机资源；使用非GUI模式与-Xmx2g，并由脚本持续采集CPU和可用内存，达到停止闸门时不再继续升压。

8.3 400线程不等于400 RPS

JMeter标准线程组属于闭环模型：一个线程必须等上一次模型回答完成后才发送下一次请求。

估算关系：

text
吞吐量（请求/秒）约等于 并发线程数 / 平均完整响应时间（秒）

例如400线程、平均响应时间20秒：

text
400 / 20 = 约20 RPS

所以本测试声明的是“最高400并发线程”，不能在报告中写成“400 RPS”，除非JMeter实际吞吐量确实达到400次/秒。

9. T2：流式连接专项测试

非流式五档结束并确定系统稳定区间后，再执行流式专项。流式请求Body仅修改：

json
"stream": true

Header改为：

http
Accept: text/event-stream

流式专项仍属于同一轮完整执行，但只选择25、200、400三个有代表性的并发档，每线程10次：

阶段并发线程每线程循环请求总数Ramp-up
S1251025030秒
S2200102,000180秒
S3400104,000300秒

流式专项共计：

text
250 + 2,000 + 4,000 = 6,250次模型请求

流式阶段没有采用50循环，是因为其目标是验证SSE长连接、首Token、持续输出和断流情况；最高档4,000个流式样本已足以做首轮判断，同时避免整个单轮方案膨胀到接近60,000次调用。

流式专项关注：

  • HTTP响应是否为text/event-stream。
  • SSE数据是否持续返回。
  • 是否以data: [DONE]正常结束。
  • 流中是否出现业务error。
  • 中途断流率。
  • 连接重置、读取超时和网关主动断开数量。
  • 平台活动连接数与上游连接池占用。
  • 供应商首Token时间和完整生成时间。

重要限制：JMeter普通HTTP Request记录的Elapsed是完整SSE流结束时间，Latency也不能直接等同于大模型首Token时间TTFT。若验收要求TTFT，优先从平台服务端日志采集upstream_first_token - upstream_start，或者增加专门的SSE分块计时脚本。

10. T3：恢复性验证

400线程阶段结束后等待2分钟，再执行：

text
线程数：1
循环次数：10
Ramp-up：1秒
stream：false

恢复通过条件：

  • 10次请求全部成功。
  • 不再持续出现429、5xx、超时或连接重置。
  • 恢复阶段P95不高于T0基线P95的1.5倍，或满足项目既定SLA。
  • 平台CPU、内存、线程池、连接池和队列回落。
  • 供应商上游排队和错误率回落。

如果高压停止后仍持续异常，应记录“高压后未及时恢复”，这本身就是重要性能缺陷。

11. JMeter测试计划组件树

建议建立一个参数化JMX，所有梯度复用同一份文件：

text
测试计划：KIMI-K3-API性能压测
├─ 用户定义的变量
├─ HTTP请求默认值
├─ HTTP信息头管理器
├─ 线程组：KIMI-K3固定模型
│  ├─ HTTP请求：POST-chat-completions
│  ├─ 响应断言：HTTP-200
│  ├─ JSON JMESPath断言：回答非空
│  ├─ JSR223断言：业务结构和内容合理
│  └─ 常数定时器（首轮关闭，可选）
└─ 简单数据写入器

正式压测时不要启用：

  • 查看结果树（View Results Tree）
  • 聚合报告GUI监听器
  • 图形结果（Graph Results）
  • 响应数据完整写入JTL
  • 请求Header完整写入JTL
  • 响应Header完整写入JTL

这些组件会消耗大量内存，可能导致压测机成为瓶颈。

14. JTL保存原则

正式JTL只保留分析性能所需字段：

  • 时间戳
  • Elapsed
  • Label
  • Response Code
  • Success
  • Failure Message
  • Bytes / Sent Bytes
  • Latency
  • Connect Time
  • Thread Name

不保存：

  • 完整请求Body
  • 完整模型回答
  • API Key
  • 请求Header
  • 响应Header
  • 成功样本Response Data

否则最高档20,000次非流式模型回答和4,000次流式回答可能使JTL迅速膨胀，并导致JMeter内存或磁盘先成为瓶颈。

16. 停止条件

任一条件满足时立即停止继续升压：

  1. 当前阶段5xx错误率达到或超过2%。
  2. 429达到或超过5%，并且已确认不是预期限流策略。
  3. 连续出现连接重置、连接超时或读取超时。
  4. P95达到基线P95的3倍以上并持续恶化。
  5. 吞吐量不再增长，但并发、排队和响应时间继续增长。
  6. 平台CPU、内存、线程池或连接池持续超过85%。
  7. 数据库连接池耗尽，计费、消费记录或日志队列持续积压。
  8. 供应商持续返回429、5xx或大量主动断流。
  9. JMeter压测机CPU持续超过85%。
  10. JMeter出现OutOfMemoryError、频繁Full GC或可用内存过低。
  11. 发现影响环境稳定或其他测试人员工作的异常。

停止后应保存当前JTL、HTML报告、平台监控截图和服务日志时间区间，不应直接重跑覆盖现场。

20. 平台与供应商瓶颈归因

建议平台日志为每个请求记录以下时间点：

text
request_start
auth_end
route_end
upstream_start
upstream_first_token
upstream_end
record_end
request_end

可以计算：

text
鉴权耗时 = auth_end - request_start
路由及平台前置耗时 = upstream_start - auth_end
供应商首Token时间 = upstream_first_token - upstream_start
供应商完整生成时间 = upstream_end - upstream_start
平台计费/日志后置耗时 = request_end - upstream_end
端到端耗时 = request_end - request_start

典型判断：

现象优先怀疑方向
平台CPU/线程池/连接池饱和，上游耗时稳定平台瓶颈
平台前置耗时增长，上游尚未开始平台鉴权、路由或排队瓶颈
upstream_start之后耗时暴涨，供应商429/5xx增加KIMI K3供应商瓶颈或限流
平台和供应商都正常，但JMeter CPU/GC异常压测机瓶颈，结果无效
吞吐不增、响应时间增、供应商排队增供应商达到容量拐点
模型返回已完成，但日志/计费写入积压平台后置链路瓶颈

仅凭JMeter端到端响应时间不能直接认定“供应商性能不足”，必须结合上游调用指标或供应商直连对照。
