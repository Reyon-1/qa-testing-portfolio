# AI 大模型 API 性能压测

对 **AI 运营平台** 的 `/v1/chat/completions` 接口做端到端性能压测，
覆盖两个大模型：**KIMI K3** 与 **GLM 5.2**。

压测目标是找出容量拐点，而不是跑出一个好看的数字——因此每个阶段都设置了
**升级闸门**（失败率、窗口失败率、恢复阈值），一旦触发就优雅停止，
不继续制造无效请求。

---

## 一、核心结论

### KIMI K3

| 阶段 | 并发 | 实际样本 | 成功/失败 | 成功率 | 有效 RPS | P95(ms) | P99(ms) |
|---|---:|---:|---:|---:|---:|---:|---:|
| T0 基线 | 1 | 3 | 3/0 | 100% | 0.044 | 28,931 | 28,931 |
| P1 | 25 | 500 | 499/1 | 99.8% | 1.278 | 23,756 | 31,213 |
| P2 | 50 | 1,000 | 1,000/0 | **100%** | **1.781** | 33,080 | 39,434 |
| P3 | 100 | 1,297 | 920/377 | 70.93% | 1.499 | 58,630 | 67,156 |
| T3 恢复 | 1 | 10 | 10/0 | 100% | 0.055 | 37,291 | 37,291 |

**容量拐点在 50～100 线程之间。** 50 线程 1,000 请求成功率 100%；
升到 100 线程后出现 377 个 HTTP 502（失败率 29.07%），
有效成功吞吐反而从 1.781 RPS 掉到 1.499 RPS。

关键观察：502 高度集中在 **30～32 秒**，呈现明显固定超时特征，
而非随机崩溃；错误连续覆盖约 7 分 35 秒。

### GLM 5.2

| 阶段 | 并发 | 实际样本 | 成功/失败 | 成功率 |
|---|---:|---:|---:|---:|
| P1 | 25 | 500 | 490/10 | 98.0% |
| P2 | 50 | 1,000 | 982/18 | 98.2% |
| P3（旧模型名） | 100 | 1,036 | 866/170 | 83.59% |
| P3（当前模型名） | 100 | 1,512 | 1,256/256 | 83.07% |
| T3 恢复 | 1 | 10 | 0/10 | 账户阻塞 |

**100 线程稳定复现容量失稳**，用新旧两个模型名称各验证一次，
失败率分别为 16.41% 和 16.93%，HTTP 502 率 15.25% / 15.28%，
说明不是命名问题而是真实容量瓶颈。

值得注意：T3 恢复阶段 10 次全部返回 `overdue-payment`（账户欠费），
属于**账户状态阻塞**而非技术恢复失败，因此该轮恢复能力**无法判定**——
报告中如实记录了这一点，没有粉饰成"通过"。

## 三、技术栈与方法

| 维度 | 做法 |
|---|---|
| 压测工具 | Apache JMeter 5.6.3，非 GUI 模式 |
| 并发模型 | 闭环并发（线程组 × 循环次数） |
| 执行编排 | PowerShell 脚本驱动，支持 `-StartAt` 断点续测 |
| 结果采集 | JTL 原始样本 + summary JSON + 阶段汇总 CSV |
| 报告生成 | JMeter Dashboard + 自动生成 Markdown 报告 |
| 环境监控 | 本机资源采样（CPU/内存）随压测同步记录 |

**闸门设计**：每阶段结束后校验失败率与窗口失败率，
超过阈值则触发紧急闸门优雅停止，避免污染被测环境。

## 四、复现方式

需要 JMeter 5.6.3+ 与一个可用的模型 API Key：

```powershell
# 1. 修改执行脚本里的地址与密钥（不要提交真实密钥）
#    Accept / Model / ApiKey 通过 -J 参数注入
$env:API_KEY = '<你的密钥>'

# 2. 执行压测（支持断点续测）
cd "KIMI K3 压测\JMeter脚本"
.\执行KIMI-K3压测.ps1

# 3. 结果输出到 原始结果\（同时会生成 JMeter Dashboard 目录）
```

`-J` 参数：`host`、`model`、`stream`、`accept`、`apiKey`。
