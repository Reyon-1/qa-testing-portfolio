针对 KIMI K3 与 GLM 5.2 两条模型链路，通过 OpenAI 兼容接口 POST /v1/chat/completions 开展闭环并发梯度压测，定位容量拐点、错误特征与高压后恢复能力。

核心结论：两模型容量拐点均落在 50 ~ 100 线程之间，100 线程档一致判定不通过

KIMI K3 在 50 线程、1,000 请求下成功率 100%，为已确认的最高稳定并发；升至 100 线程后 HTTP 502 失败率达 29.07%， 触发停止条件后优雅终止，未继续执行 200 / 400 线程及正式流式并发阶段。
GLM 5.2 在 25 / 50 线程成功率分别为 98.0% / 98.2%，仍存在 300 秒读取超时；两次 100 线程验证均稳定复现失稳， 当前模型名下失败率 16.93%（502 率 15.28%）。
两轮压测的 502 响应均表现为固定 297 字节、约 30 秒返回，高度符合平台网关统一上游超时错误页特征， 但受限于缺少服务端分段监控，暂不能在平台与供应商之间做确定归因；恢复验证因上游账户 overdue-payment 阻塞而无法判定。

100 线程专项分析

两模型在 100 线程档均出现明显容量失稳，且错误特征高度一致。

KIMI K3 · 100 线程错误特征

  • 共 377 个 HTTP 502，失败率 29.07%，触发 5xx 达 2% 的停止条件
  • 377 个响应记录大小全部精确为 297 字节，无任何波动
  • 502 响应高度集中在 30 ~ 32 秒，平均值 30.474 秒，呈现明显固定超时特征
  • 错误连续覆盖约 7 分 35 秒（21:13:06 ~ 21:20:41）
  • 连接建立时间多数为 0，说明连接复用成功，请求已到达平台前置服务

GLM 5.2 · 100 线程错误特征

  • 旧模型名 502 率 15.25%、当前模型名 502 率 15.28%，仅相差 0.03 个百分点
  • 说明修改模型 API 名称没有消除并发瓶颈，问题稳定复现，不像偶发网络抖动
  • 231 个 502 响应同样均为 297 字节、约 30 秒返回
  • P99 约 300 秒由 300 秒读取超时拉高，与 502 属不同错误类型
  • 并发升至 100 后，有效成功吞吐未随线程数线性增长，错误率突破 10% 升级闸门

瓶颈归因（证据边界）

  • 测得的是「JMeter → Token平台 → 供应商 → Token平台 → JMeter」的端到端性能
  • 502 统一 297 字节 + 固定约 30 秒返回窗口，高度符合平台 Nginx / 网关等待上游超时后生成统一错误页的特征

  • 正式 JTL 不保存批量响应 Body 与 Header，无法仅凭客户端数据区分 502 由平台网关还是供应商上游产生

一、结论摘要

本轮已确认的最高稳定并发为 50线程。在50线程、1,000个请求下成功率为100%，无429、5xx、超时或连接重置，端到端吞吐量为1.781 RPS，P95为33.080秒，P99为39.434秒。

100线程阶段发生明显容量失稳。原计划2,000个请求，执行到1,297个样本时因达到停止条件而优雅终止，其中920个成功、377个HTTP 502，失败率29.07%。因此未继续执行200、400线程以及正式流式并发阶段，避免继续制造无效请求和扩大环境影响。

高压停止并冷却2分钟后，1线程连续恢复验证10/10成功，无502、429、超时或连接重置。恢复阶段P95为37.291秒，比正式T0基线P95 28.931秒高28.9%，仍低于“基线1.5倍”的恢复阈值43.397秒，因此恢复验证通过。

对外OpenAI兼容接口的主请求不需要登录Token，也不使用平台页面的登录会话。每次请求只包含一个user消息，因此天然是独立单轮请求。

5. 为什么主测试采用API Key直调

平台模型体验页面内部使用登录会话，并调用：

http

模型体验页面适合验证页面功能，但不是本次负载测试主入口，原因如下：

  1. 页面调用会混入登录Token、页面逻辑、前端渲染和浏览器资源消耗。
  2. 400个浏览器会话会先压垮压测机，不能代表API服务真实容量。
  3. 用户实际要验证的是平台API Key调用链路。
  4. POST /v1/chat/completions能稳定固定model=kimi-k3(压测)。
  5. JMeter可以直接对API采集状态码、吞吐量、分位响应时间和错误类型。

8.2 为什么采用20、20、20、30、50次折中循环

  • 25至100线程使用20次循环，兼顾样本量和低压阶段执行时间。
  • 200线程提高到30次循环，获得6,000个中高压样本。
  • 400线程提高到50次循环，获得20,000个最高压样本，用一轮同时观察容量和持续稳定性。
  • 正式JTL不保存完整回答，所以样本量增加后主要增加测试时长和服务端负载，不应显著扩大JMeter内存占用。
  • 本轮结束后不再安排相同梯度的第二轮50循环复测。

循环次数主要影响持续时间和样本数；线程数才直接决定瞬时并发压力。因此不能把“本机能开400线程”理解为“每个线程必须循环500次”。

正式执行前已重新核实本机资源；使用非GUI模式与-Xmx2g，并由脚本持续采集CPU和可用内存，达到停止闸门时不再继续升压。

8.3 400线程不等于400 RPS

JMeter标准线程组属于闭环模型：一个线程必须等上一次模型回答完成后才发送下一次请求。

估算关系：

text
吞吐量（请求/秒）约等于 并发线程数 / 平均完整响应时间（秒）

例如400线程、平均响应时间20秒：

text
400 / 20 = 约20 RPS

所以本测试声明的是“最高400并发线程”，不能在报告中写成“400 RPS”，除非JMeter实际吞吐量确实达到400次/秒。

16. 停止条件

任一条件满足时立即停止继续升压：

  1. 当前阶段5xx错误率达到或超过2%。
  2. 429达到或超过5%，并且已确认不是预期限流策略。
  3. 连续出现连接重置、连接超时或读取超时。
  4. P95达到基线P95的3倍以上并持续恶化。
  5. 吞吐量不再增长，但并发、排队和响应时间继续增长。
  6. 平台CPU、内存、线程池或连接池持续超过85%。
  7. 数据库连接池耗尽，计费、消费记录或日志队列持续积压。
  8. 供应商持续返回429、5xx或大量主动断流。
  9. JMeter压测机CPU持续超过85%。
  10. JMeter出现OutOfMemoryError、频繁Full GC或可用内存过低。
  11. 发现影响环境稳定或其他测试人员工作的异常。

📋 GLM 5.2 压测方案

测试方案 · 2026-09-11

示例运营平台 GLM 5.2 API性能压测方案

测试环境：http://198.51.100.10/v1

唯一模型：glm-5.2-test

工具：Apache JMeter 5.6.3，非GUI模式

固定问题：给出一套成都旅游一日游方案，50字左右

请求口径

json
{
  "model": "glm-5.2-test",
  "messages": [
    {
      "role": "user",
      "content": "给出一套成都旅游一日游方案，50字左右"
    }
  ],
  "temperature": 0.2,
  "max_tokens": 32768,
  "stream": false
}

GLM 5.2会先输出推理Token。实测max_tokens=100和512时推理耗尽上限、正文为空；1024三次预检仍有一次正文为空；2048在25线程校准运行358个样本中出现7次空正文；8192在25线程校准运行482个样本中仍出现3次超长推理导致的空正文。因此正式压力测试采用32768。该参数是输出上限，模型以finish_reason=stop完成时会提前结束，并非每次强制生成32768 Token。
