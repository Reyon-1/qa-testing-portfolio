一、结论摘要

GLM 5.2在25线程和50线程阶段均完成全部计划请求，成功率分别为98.0%和98.2%。两档错误率均低于当前10%阶段升级闸门，但仍存在300秒读取超时，不能表述为零错误稳定运行。

100线程在旧、新模型名称下进行了两次验证，均稳定复现容量失稳。旧名称运行到1,036/2,000个样本时失败率16.41%，新名称运行到1,512/2,000个样本时失败率16.93%；HTTP 502率分别为15.25%和15.28%。新名称运行期间连续窗口失败率达到约30%至35%，触发紧急闸门后优雅停止。因此100线程不通过，未继续执行200、400线程及正式流式并发阶段。

新名称100线程总RPS为1.787，但包含231个HTTP 502和25个超时，有效成功RPS约1.484。高压后的恢复验证因上游账户返回overdue-payment而全部快速失败，属于账户状态阻塞，不是技术恢复失败，因此无法判定恢复能力。

六、闸门与停止口径

  1. 运行中连续统计窗口失败率达到30%，立即使用shutdown.cmd优雅停止并保留JTL。
  2. 阶段结束后总体失败率或主要错误分类达到10%，禁止升级。
  3. HTTP 401或403立即停止。
  4. 压测机CPU或内存持续过载时停止。

30%是运行中紧急保护线，10%是档间升级门槛。当前模型P3同时满足紧急停止和禁止升级条件。

九、最终判定

  1. 25和50线程已完整执行，成功率98.0%和98.2%，但存在超时或空回答。
  2. 容量拐点位于50至100线程之间；当前梯度不能给出更精确阈值。
  3. 100线程两次均不通过；当前模型名下失败率16.93%，其中502率15.28%。
  4. 200和400线程未执行，不能宣称不通过或平台支持该并发。
  5. 正式流式并发未执行，仅确认1线程SSE和[DONE]闭环正常。
  6. 高压后恢复因overdue-payment无法判定。
  7. 未发现足以解释目标端连续502的发压机资源瓶颈。
  8. 问题位于Token平台至GLM供应商链路；无服务端分段证据，暂不能确定责任方。

十、下一步建议

  1. 恢复阿里云Model Studio账户，以单请求HTTP 200且正文非空作为继续条件。
  2. 补做T3恢复验证，避免把欠费数据混入性能统计。
  3. 核对Nginx日志中的upstream timed out、上游地址和约30秒超时配置。
  4. 采集平台排队、上游连接池、首Token时间、完整响应时间及供应商RPM/TPM/并发指标。
  5. 修复后用60、70、80、90线程定位50至100间的容量拐点，不直接冲击200或400线程。
  6. 中间梯度稳定后单独执行流式并发，流式和非流式必须分开统计。

11.6 续测闸门口径

本次采用两级闸门：

  1. 运行中连续统计窗口失败率达到30%，立即优雅停止当前档。
  2. 阶段完成后总体失败率或主要错误分类达到10%，禁止升级到下一档。
  3. 401/403立即停止。
  4. 压测机持续过载立即停止。

30%适合保护正在进行的极限压力阶段；10%适合决定是否还能安全升级。不能只使用30%作为升级标准，否则系统已经明显失稳时仍会继续冲击200/400线程。

11.9 续测归因判断

已确认502由平台前置Nginx/网关统一返回，但仅凭客户端结果还不能断定真正慢点在平台内部还是提供商。需要结合以下服务端证据：

  1. Nginx错误日志中的upstream timed out及其upstream地址。
  2. 平台从request_start到upstream_start的排队时间。
  3. 平台上游HTTP连接池等待数和耗尽情况。
  4. 从upstream_start到upstream_first_token/upstream_end的提供商耗时。
  5. 供应商并发、RPM、TPM、排队和错误日志。

十三、证据边界

本报告测得的是“JMeter → Token平台 → GLM 5.2供应商 → Token平台 → JMeter”的端到端性能。当前没有平台服务器CPU、线程池、上游连接池、数据库/计费队列以及供应商侧排队和GPU指标，因此不能只凭客户端502和响应时间断定责任一定属于平台或供应商。

本报告只汇总真实执行结果。未执行的200/400线程和正式流式并发不作性能判定；欠费产生的HTTP 400仅作为阻塞证据，不计入正常负载阶段错误率。后续结果统一追加到本报告，不再创建单独续测报告。
