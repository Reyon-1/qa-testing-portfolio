# 示例运营平台 Key接入场景 性能压测方案 v2

> 方案版本：v2（流式优先）  
> 编制日期：2026-09-13  
> 测试环境：`http://198.51.100.10/v1`  
> 测试接口：`POST /v1/chat/completions`  
> 测试工具：Apache JMeter 5.6.3，非GUI模式，闭环并发模型  
> 固定问题：`给出一套成都旅游一日游方案，50字左右`  
> 适用场景：用户通过 API Key 将平台接入自有 Agent 使用  
> 本轮目标模型：`glm-5.2-test`（结果输出至 `压测报告\GLM5.2 流式\`）  
> 流式加压上限：**500 线程**  
> 调用额度：约 26,000 次，本方案预算约 12,830 次

## 一、编制原因（相比 v1 的改动）

v1 方案在 2026-09-11 执行后暴露三个问题，v2 针对性修正：

| v1 的问题 | 造成的后果 | v2 的改动 |
|---|---|---|
| 流式阶段排在非流式之后 | 非流式 P3 失稳后，流式 S1~S3 全部未执行 | **流式改为独立轨道，优先执行** |
| 流式梯度为 25 → 200 → 400 | 中间无数据，无法定位流式失稳点 | **改为 50 / 100 / 200 / 400 / 500 共 5 档** |
| 无流式严格断言 | 流式失败藏在 HTTP 200 之后，可能静默通过 | **新增流式断言清单（见第六章）** |

## 二、测试目标

1. **主目标**：定位流式并发下的容量拐点。**流式采用 50 / 100 / 200 / 400 / 500 共 5 档梯度，最高加压至 500 线程**，明确流式最高稳定并发。
2. 对照非流式容量：v1 已知 50 线程稳定、100 线程失稳，本次保留 1 档同期对照（可选）。
3. 对比流式与非流式的失稳点，判断瓶颈倾向（平台侧或供应商侧）。
4. 验证各档高压后的恢复能力。

**成本约束**：总调用额度约 26,000 次。本方案全部执行约 12,830 次，仅为额度一半；并遵循「失稳即停」原则，实际消耗通常更低。

**本次不测**：多轮上下文、长上下文、工具调用（tools）、模型体验页面、登录与验证码。

## 三、测量能力边界

本方案使用 JMeter，下表明确界定哪些指标测、哪些不测。

| 指标 | 能否测量 | 说明 |
|---|---|---|
| 成功率 | 能 | |
| 流式端到端总耗时 | 能 | 从发起到收到完整响应 |
| SSE 完整性（收到 `[DONE]`） | 能 | 响应体断言 |
| 正文非空 | 能 | 拼接后校验 |
| SSE `data:` 事件数 | 能 | 用于协议结构校验；不能据此判断事件是否实时到达 |
| **TTFT（首 Token 时间）** | **不测** | JMeter 无法测量 |
| **chunk 间隔 / 生成速度** | **不测** | 同上 |

**说明**：JMeter 的 HTTP 请求会等待完整响应后才结束，因此本方案的流式验证覆盖的是「**协议正确性 + 端到端完成能力**」，不包含首字延迟。

如需评估 TTFT，必须使用支持流式读取的采样器（如 JSR223 + 流式 HttpClient），或从平台服务端分段日志（`upstream_first_token`）中提取。本方案不包含该项。

## 四、请求输入设计

### 4.1 统一请求体

**全部档位、全部轨道使用完全相同的请求体，唯一变量是 `stream`。**

```json
{
  "model": "glm-5.2-test",
  "messages": [
    {
      "role": "user",
      "content": "给出一套成都旅游一日游方案，50字左右"
    }
  ],
  "temperature": 0.2,
  "max_tokens": 32768,
  "stream": true
}
```

- 轨道 B（流式）：`stream = true`
- 轨道 A（非流式对照）：`stream = false`

**除 `stream` 外，任何参数都不得在档位之间变动。**

### 4.2 请求头

```http
POST http://198.51.100.10/v1/chat/completions
Authorization: Bearer <API_KEY>
Content-Type: application/json
Accept: text/event-stream          # 流式
Accept: application/json           # 非流式
```

### 4.3 参数取值依据

| 参数 | 取值 | 依据 |
|---|---|---|
| `model` | `glm-5.2-test` | 本轮目标模型，须与 `GET /v1/models` 返回的精确值完全一致 |
| `messages` | 单条 `user` 消息 | 单轮请求，不携带上下文，保证各档位可比 |
| `temperature` | `0.2` | 降低随机性，使各档输出的长度与耗时相对可比 |
| `max_tokens` | `32768` | GLM 5.2 先输出推理 Token。实测 `100` / `512` 会因推理耗尽上限导致正文为空，`2048` 仍偶发空正文，`32768` 为经过验证的可用值 |
| `stream` | 流式 `true` / 非流式 `false` | 本方案的**核心对照变量** |

### 4.4 固定问题

统一使用：

```text
给出一套成都旅游一日游方案，50字左右
```

**为什么固定同一问题**：

1. 各档位请求完全一致，成功率、耗时、错误率可直接横向比较
2. 输出长度可预期，避免长尾输出污染 P95 / P99
3. 与 v1 使用同一问题，便于与非流式历史数据对照

**执行约束**：不得随机替换问题，不得携带上一轮问答，不得在同一上下文中累计消息。

### 4.5 已知局限：缓存效应

固定问题存在一个副作用：**供应商若启用前缀缓存（prefix caching），同一问题反复请求可能命中缓存，使 prefill 阶段变快，导致结果偏乐观。**

真实 Agent 场景下，system prompt 相对固定（可缓存），但对话历史持续变化（无法完全缓存），实际成本介于「全缓存」与「无缓存」之间。

**处置方式**：

- 本方案优先保证**档位间可比性**，仍采用单一固定问题
- 报告中必须注明该局限
- 若需要更贴近真实的评估，可改用 2~3 个长度相近的等价问题轮换，但这会降低档位间的严格可比性，**不建议与本次测试混用**

## 六、断言清单

### 6.1 为什么流式断言是必须的

**JMeter 会自动把 HTTP 4xx / 5xx 标记为失败，但不会把「HTTP 200 但内容截断」标记为失败。**

流式的失败恰恰大多藏在 200 后面：

| 失败形态 | HTTP 状态 | JMeter 默认是否判失败 |
|---|---|---|
| 网关超时统一错误页 | 502 | 会 |
| 上游中途断开 | 200（响应头已发出） | **不会** |
| 内容被截断、无 `[DONE]` | 200 | **不会** |
| 只输出推理内容、正文为空 | 200 | **不会** |
| 网关缓冲导致伪流式 | 200 | **不会** |

**因此必须用显式断言覆盖上述情形，否则流式档位会出现「假通过」。**

### 6.2 流式断言清单

| # | 断言项 | 判定标准 | 不通过的典型原因 |
|---|---|---|---|
| 1 | HTTP 状态码 | = 200 | 502 网关错误、401 / 403 鉴权失败 |
| 2 | 响应类型 | `Content-Type` 含 `text/event-stream` | 平台未按流式返回 |
| 3 | SSE 事件结构 | 非空 `data:` 事件数 ≥ 2，且至少一个事件包含非空 `choices` | 只返回终止标记、协议体缺失 |
| 4 | 结束标志 | `[DONE]` 逐行精确匹配、仅出现一次且是最后一个 `data:` 事件 | 连接中途断开、重复结束、结束后仍混入数据 |
| 5 | 正文内容 | 全部 `choices[0].delta.content` 拼接并 `trim()` 后非空 | 模型只输出推理、正文仅空白 |
| 6 | 事件合法性 | 每个非 `[DONE]` 的 `data:` 事件均可独立解析为 JSON | 事件被截断或协议错误 |
| 7 | 业务错误 | 任一事件均不含非空 `error` 字段 | 上游在 HTTP 200 流中返回业务错误 |

### 6.3 完整 JSR223 断言（Groovy）

一次性覆盖第 3~7 项：

```groovy
import groovy.json.JsonSlurper

def body = prev.getResponseDataAsString()
def datas = body.readLines()
    .collect { it.trim() }
    .findAll { it.startsWith('data:') }
    .collect { it.substring(5).trim() }
    .findAll { it }

def doneIndexes = datas.withIndex().findAll { item, index -> item == '[DONE]' }.collect { it[1] }
def hasDone   = !doneIndexes.isEmpty()
def payloads  = datas.findAll { it != '[DONE]' }
def slurper   = new JsonSlurper()
def content   = new StringBuilder()
def reasoning = new StringBuilder()
def apiErrors = []
def badChunks = 0
def choiceEvents = 0

payloads.each { p ->
    try {
        def o = slurper.parseText(p)
        if (o?.error) apiErrors << (o.error?.message ?: o.error.toString())
        def ch = o?.choices
        if (ch instanceof List && ch.size() > 0) {
            choiceEvents++
            def d = ch[0]?.delta
            if (d?.content)           content.append(d.content)
            if (d?.reasoning_content) reasoning.append(d.reasoning_content)
        }
    } catch (Exception e) {
        badChunks++
    }
}

def errs = []
if (datas.size() < 2)       errs << "SSE事件数=${datas.size()}"
if (!hasDone)               errs << "未收到[DONE]（响应可能被截断）"
if (doneIndexes.size() > 1) errs << "[DONE]重复"
if (hasDone && doneIndexes[0] != datas.size() - 1) errs << "[DONE]不是最后一个data事件"
if (choiceEvents == 0)      errs << "未收到choices事件"
if (content.toString().trim().isEmpty()) errs << "正文为空"
if (badChunks > 0)          errs << "非法JSON分片=${badChunks}"
if (apiErrors)              errs << "流内业务错误=" + apiErrors.take(1).join('')

if (errs) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage(errs.join('; '))
}
```

**脚本设计说明**：

| 设计点 | 原因 |
|---|---|
| `trim()` 后再匹配 `data:` | 兼容 `data: ` 与 `data:` 两种写法（SSE 规范中冒号后的空格可选） |
| `[DONE]` 用**逐行精确匹配**而非 `body.contains()` | 避免正文中偶然出现该字符串造成误判 |
| `[DONE]` 必须唯一且位于最后 | 避免重复终止标记或终止后仍出现异常数据被误判成功 |
| 每个分片**单独解析 JSON** | 能定位分片级截断，而不只是整体成败 |
| 同时累计 `reasoning_content` | 用于区分「正文为空」与「只输出了推理内容」，便于事后分析 |
| 检查分片内 `error` 字段 | 上游可能在流中返回业务错误而不是断连 |
| 不用 `data:` 行数判断实时流式 | 普通 JMeter HTTP 采样器在完整响应后统一交给断言，事件数只能证明 SSE 结构，不能证明 TTFT、分片间隔或网关未缓冲 |

### 6.4 非流式断言

- HTTP 状态码 = 200
- 响应体可解析为合法 JSON
- `choices[0].message.content` 非空
- 响应中不含 `error` 字段

### 6.5 JMeter 配置注意事项

1. 确认 **「Ignore Status」未勾选**。若勾选，4xx / 5xx 不会被判失败，502 会被漏统计。
2. 确认监听器**不限制响应体大小**，避免大响应被截断后误判为「内容为空」。
3. 流式的读取超时与非流式**语义不同**（流式为分片间隔超时），需单独设置并记录实际取值。
4. 断言必须挂载在**每个档位**的 HTTP 请求上，不能只在预检时启用。
5. **断言自检**：预检阶段先用一个已知会失败的场景（如临时改错模型名或断网）验证断言确实能触发失败，确认断言本身有效后再正式开压。

## 七、执行范围

### 轨道 B：流式（**主测，5 档，最高加压至 500 线程**）

| 档位 | 线程 | 每线程循环 | 计划请求 | Ramp-up | 冷却 | 满并发观察窗口* |
|---|---:|---:|---:|---:|---:|---:|
| T0-S | 1 | 3 | 3 | 1 秒 | - | - |
| S1 | 50 | 20 | 1,000 | 30 秒 | 3 分钟 | 约 470 秒 |
| S2 | 100 | 16 | 1,600 | 40 秒 | 4 分钟 | 约 360 秒 |
| S3 | 200 | 13 | 2,600 | 45 秒 | 4 分钟 | 约 280 秒 |
| S4 | 400 | 9 | 3,600 | 30 秒 | 5 分钟 | 约 195 秒 |
| S5 | 500 | 7 | 3,500 | 30 秒 | 5 分钟 | 约 145 秒 |

注：上表「满并发观察窗口」按单请求约 25 秒估算，计算方式为 `循环数 × 单请求耗时 − Ramp-up`。

**梯度设计说明**：

- **50 → 100 → 200 → 400 → 500**，覆盖到 500 线程。受测试成本约束，不设置 25 / 75 / 150 / 300 等中间档。
- **S1（50 线程）是关键的对照锚点。** 非流式在该并发下为 100% 成功，流式必须独立验证。若流式在 50 即失稳而非流式通过，属于**重大发现**，应立即单独记录并上报。
- **S2（100 线程）是另一个锚点**：非流式在该并发下已失稳（KIMI 失败率 29.07%、GLM 16.93%），可用于对比两种模式的失稳程度。
- **S4 与 S5 共用同一 Ramp-up 逻辑**，400 与 500 之间仅差 25%，用于确认 400 附近是否存在容量平台期或二次下跌。
- **循环数不宜过少**，原因有三：① 样本量决定 P95/P99 的可信度，样本低于 500 时 P99 基本是噪声；② 循环数决定**满并发观察窗口**的长度，过短会在系统进入稳定态之前就结束，无法判断失败是偶发还是持续（v1 中 KIMI 100 线程的 502 连续持续约 7 分 35 秒才被判定为稳定失稳）；③ 每线程迭代次数太少，观察不到单线程内的性能退化（连接泄漏、内存增长等）。
- **循环数的下限约束**：`循环数 ≥ Ramp-up ÷ 单请求耗时 + 2`。否则先启动的线程会在后启动线程尚未到齐时结束，导致**实际未达到目标并发**。当前配置已满足该约束并留有明显富余。
- 若需要更精确的拐点，在首个失稳档与上一档之间补测一档即可，不必重跑全部梯度。

## 八、闸门与停止口径

沿用 v1 的两级闸门，但改为**每轨道独立评估**。

### 7.1 运行时紧急闸门（30%）

任一档的连续统计窗口失败率达到 30%，立即使用 `shutdown.cmd` 优雅停止并保留 JTL。

### 7.2 档间升级门槛（10%）

单档结束后，以下任一分类达到 10%，该档判为失稳，停止本轨道升级：

- 总体失败率
- HTTP 5xx 率
- 读取超时率
- SSE 不完整率
- 空正文率

### 7.3 立即停止

- 出现 HTTP 401 或 403
- 压测机 CPU 或内存持续过载

### 7.4 轨道独立性（v2 关键改动）

**轨道 A 判为失稳不阻塞轨道 B 执行，反之亦然。** 两条轨道各自独立门禁、独立判定、独立出结论。

## 十、验收标准

| 结论项 | 判定方式 |
|---|---|
| 流式最高稳定并发 | 失败率 < 10% 的最高档 |
| 流式容量拐点 | 首个失稳档与上一档之间 |
| 非流式精细拐点 | 同上 |
| 流式与非流式对比 | 比较两轨道失稳点高低 |
| 恢复能力 | T3 成功率 100%，且 P95 ≤ T0 基线 P95 的 1.5 倍 |

### 归因参考

在无服务端分段数据时，可通过以下现象做倾向性判断：

| 现象 | 倾向 |
|---|---|
| 流式明显早于非流式失稳 | 瓶颈偏向连接占用与网关转发（平台侧） |
| 两者失稳点接近 | 瓶颈偏向供应商推理能力 |
| 换模型后失稳点差异明显 | 瓶颈偏向供应商侧 |

**上述仅为倾向性判断，最终归因须结合服务端日志。**

## 十一、未执行档位的表述口径

- **流式**：本次最高加压至 500 线程（S5）。若某档未执行（例如因前档失稳而停止升级），该档**不作任何性能判定**，不得表述为“不通过”，也不得宣称平台支持该并发。
- **非流式**：本次仅保留 100 线程一档对照。**200 / 400 / 500 线程不纳入非流式范围**，不得表述为“不通过”，也不得宣称平台支持该并发。
- 因账户状态阻塞产生的 HTTP 400：仅作为阻塞证据，不计入正常负载阶段错误率。

## 十二、已知限制

1. **无 TTFT 数据**。受工具限制，本方案不产出首 Token 时间；流式体验的核心指标需另行评估。
2. **端到端测量**。测得的是「JMeter → Token平台 → 供应商 → Token平台 → JMeter」全链路表现，无服务端分段监控时不能单方归因。
3. **单一固定问题**。供应商若启用前缀缓存，可能使结果偏乐观。
4. **闭环并发模型**。与真实开环流量存在差异，闭环会自我节流，可能低估真实故障严重程度。
5. **未覆盖**多轮上下文、长上下文、工具调用（tools）与混合负载。

## 十三、执行顺序

```text
G0 阻塞项检查
  -> G1 配置确认（proxy_buffering 必查）
  -> G2 非流式功能预检 1×3
  -> G3 流式功能预检 1×1
  -> T0-S 流式基线 1×3
  -> 【轨道 B】流式 S1(50) -> S2(100) -> S3(200) -> S4(400) -> S5(500)
  -> T3-S 流式恢复 1×10
  -> 【轨道 A】非流式对照 A1(100)     ← 可选
  -> T3-A 非流式恢复 1×10            ← 可选
  -> 汇总出报告
```

**流式优先执行**，确保主目标数据在任何情况下都能拿到。

任一档达到失稳判定（见第八章）即停止**本轨道**升级并进入恢复验证；另一轨道不受影响。**这是成本控制的主要手段——崩了就不用再往上打。**
