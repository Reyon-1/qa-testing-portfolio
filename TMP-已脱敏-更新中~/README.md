| 模块 | 用例数 | 覆盖内容 |
|---|---:|---|
| 全局 | 136 | 登录、消息中心、待办流程、语言切换、个人中心、通道配置 |
| 概览 | 24 | KPI 指标卡、周期统计、趋势图表、筛选、空数据与异常 |
| 模型 | 352 | 模型提供商、模型管理、模型上架（多阶段表单）、路由管理 |
| 租户 | 194 | 租户管理、API Key、订阅管理、消费记录、调用日志、订单 |
| 财务 | 49 | 账单管理、发票管理与审批 |
| 运维 | 60 | 护栏策略配置、操作日志 |
| 配置 | 111 | 管理用户、角色、系统信息、币种配置、租户额度预警 |

### 结构约定

每条用例统一采用三段式，便于评审与执行：

```
tc:验证输入错误密码点击登录提示用户名或密码错误，停留在登录页
 ├─ pc:登录页已打开，用户名和密码输入框可见       ← 前置条件
 ├─ 步骤:输入 admin / 错误密码 → 输入验证码 → 点击登录
 └─ 预期:提示"用户名或密码错误"，页面停留在登录页  ← 预期结果
```

### 设计方法

等价类划分、边界值分析（3/4/20/21 字符、端口 1/65535/65536）、
判定表（组合筛选 AND 逻辑）、场景法（多阶段表单全流程）、
错误推测法（特殊字符、重名、网络异常、重复点击）、状态迁移。

### 覆盖特点

- **负向用例占比高**：122 条显式标注 `【反向】`，另有大量以「校验提示」「格式错误」为预期的用例
- **覆盖异常与边界**：空数据、加载失败、导出超限、分页边界、长度上下限、状态约束
- **校验点具体到 UI 细节**：表头列数与列名、状态标签颜色圆点、按钮 loading 与置灰、placeholder 文案、tooltip 截断

## 二、数据驱动测试数据

用于**接口自动化数据驱动测试**的边界值数据集，CSV 格式，覆盖 4 个业务模块：

| 模块 | 正向 | 逆向 | 合计 |
|---|---:|---:|---:|
| 用户新增 | 25 | 18 | 43 |
| 供应商新增 | 45 | 189 | 234 |
| 模型新增 | 34 | 138 | 172 |
| 模型上架 | 46 | 330 | 376 |
| **合计** | **150** | **675** | **825 条** |

每一条数据驱动一次完整业务流程（`建 provider → 建 model → 调 product/create → 断言 → 清理`）。
正向用例断言 `code == 200`，逆向用例断言 `code != 200`。

### 设计方法

- **边界值分析**：每字段覆盖 最小值 / 最小-1 / 最大值 / 最大+1
  （username 1↔65 字符、realName 1↔33 字符、displayName 1↔129 字符）
- **等价类划分**：合法邮箱、非法格式、空串、纯空格
- **安全载荷**：`' OR '1'='1`（SQL 注入）、`<script>alert(1)</script>`（XSS）、`../../x`（路径穿越）
- **国际化与特殊字符**：`café`、`emoji😀`、`pv-中文名`、`pv-日本語`、`pv-한국어`

### 实战发现

这批数据跑出过多个有效缺陷，含高危问题：

- `description` 字段未过滤 XSS/SQL/路径穿越载荷（**高危**）
- `tenants[].tenantId` 不校验存在性（**高风险**）
- `prices` 接受字符串/null 时返回 500 而非 400
- `sortOrder` 接受负数、`experienceEnabled` 不校验枚举
- `tokenPriceUnit` 不校验枚举且大小写不敏感

## 三、接口自动化

基于 **Apifox 测试场景**构建的管理端接口回归，覆盖 CRUD 链式回归、数据驱动边界回归
与冒烟测试三类，共 **14 个测试场景**，通过 Runner 定时执行并留存测试报告。

| 分组 | 场景数 | 覆盖内容 |
|---|---:|---|
| CRUD 链式回归 | 6 | 模型提供商、模型、模型产品、路由、角色、用户的增删改查全链路 |
| 数据驱动 | 7 | 模型提供商新增、用户新增、模型新增、模型上架 的正 / 逆向边界 |
| 冒烟测试 | 1 | 登录与各模块入口可用性 |
| 测试套件 | 1 | 全量回归测试套件，单次执行 65 个请求 |

### 链式回归的步骤设计

单接口用例只能验证「接口自己」；链式回归验证的是「**数据在多个接口之间流转后是否仍然正确**」：

```
① 分页查询模型          POST /api/model/page
② 新增模型              POST /api/model/add          → 提取 newModelId
③ 分页查询模型          POST /api/model/page         → 按名称匹配取真实 ID
④ 获取模型详情          GET  /api/model/detail/{newModelId}
⑤ 更新模型              PUT  /api/model/update
⑥ 获取模型详情          GET  /api/model/detail/{newModelId}   → 断言修改已生效
⑦ 删除模型              DELETE /api/model/delete
```

第 ⑥ 步回查是整条链路的价值所在——它断言的不是「更新接口返回 200」，
而是「**更新后的值真的被读出来了**」。

### 三段式断言

每个步骤按「协议层 → 业务层 → 数据层」校验，而不是只断言 HTTP 200：

| 层级 | 断言对象 |
|---|---|
| 协议层 | `HTTP Code` 状态码正确 |
| 业务层 | `Response JSON $.code` 业务码正确 |
| 数据层 | `Response JSON $.data.displayName` 等于预期值 |

### 变量传递

资源 ID 不硬编码，全部由前序步骤的响应提取到环境变量后引用：

| 变量 | 提取方式 |
|---|---|
| `newProviderId` | `Response JSON → JSONPath → $.data.records[0].id` |
| `newModelId` | `Response JSON → JSONPath → $.data.records[0].id` |

分页返回顺序不稳定，因此在提取前用脚本按业务主键定位本次创建的目标记录，
并显式断言必须找到——避免后续步骤用错 ID：

```js
const data = pm.response.json().data;
const found = (data.records || []).find(
  r => r.displayName === pm.iterationData.get('displayName')
);
if (found) pm.environment.set('newModelId', found.id);
```

`pm.iterationData.get(...)` 把**数据驱动**和**链式取 ID** 接了起来：
每条 CSV 记录创建的资源都能被精确定位，而不是靠"取列表第一条"碰运气。

## 四、UI 自动化

管理端 Web UI 回归测试，**47 条用例 / 14 个文件**：

| 模块 | 用例数 | 覆盖内容 |
|---|---:|---|
| 登录 | 3 | 页面结构核对、人工验证码登录、登录态持久化 |
| 概览 | 21 | 统计卡、图表渲染、时间/租户筛选、空数据与异常 |
| 模型 | 23 | 提供商 / 模型管理 / 模型上架 / 路由管理 |

### 工程做法

**Page Object 模式** —— 定位细节封装在页面类里，用例只描述业务步骤。

**Web-first 断言，零固定 sleep** —— 等加载遮罩消失是断言 `toHaveCount(0)`，
不是 `waitForTimeout(3000)`。

**接口层断言，不只看界面** —— 用例会验证搜索关键词确实进了请求体、
字典接口确实被调用。只看"表格有没有出来"会漏掉前端假数据。

**登录态双层持久化** —— 该系统 token 同时存在 Cookie 和 sessionStorage，
而 Playwright 的 `storageState` 不覆盖 sessionStorage，
必须用 `page.addInitScript` 在页面脚本执行前注入。

**Canvas 图表验证** —— ECharts 把坐标画在 Canvas 上，DOM 取不到文本，
改用 `getImageData()` 读像素确认画布真有绘制内容。

**失败自动留证** —— `trace` + `video` + `screenshot` 全开，
`npx playwright show-trace` 可回放现场。

## 五、性能压测

对 `/v1/chat/completions` 做容量测试，覆盖两个大模型。
每个阶段都设**升级闸门**（失败率、窗口失败率、恢复阈值），
触发即优雅停止，不继续制造无效请求。

### 核心结论

**KIMI K3 —— 容量拐点在 50～100 线程之间**

| 并发 | 实际样本 | 成功/失败 | 成功率 | 有效 RPS | P95(ms) |
|---:|---:|---:|---:|---:|---:|
| 1 | 3 | 3/0 | 100% | 0.044 | 28,931 |
| 25 | 500 | 499/1 | 99.8% | 1.278 | 23,756 |
| **50** | 1,000 | 1,000/0 | **100%** | **1.781** | 33,080 |
| 100 | 1,297 | 920/377 | 70.93% | 1.499 | 58,630 |

50 线程 1,000 请求成功率 100%，升到 100 线程后出现 **377 个 HTTP 502**，
有效吞吐不升反降（1.781 → 1.499 RPS）。

> 关键发现：502 高度集中在 **30～32 秒**，是固定超时特征而非随机崩溃，
> 这比单纯的"失败率高"更能指向根因。

**GLM 5.2 —— 100 线程稳定复现失稳**

用新旧两个模型名称各验证一次，失败率 16.41% / 16.93%，
证明是真实容量瓶颈而非命名问题。

> T3 恢复阶段 10 次全部返回 `overdue-payment`（账户欠费），
> 属于**账户状态阻塞**、不是技术恢复失败，因此该轮恢复能力**判定为无法判定**——
> 如实记录，没有粉饰成"通过"。

**GLM 5.2 流式（SSE）—— 同样在 50～100 并发之间见拐点**

| 并发 | 样本 | 成功率 | RPS | P95(ms) |
|---:|---:|---:|---:|---:|
| 50 | 1,000 | 99.70% | 1.4875 | 21,987 |
| 100 | 1,600 | 98.94% | 2.2514 | 45,917 |
| 200 | 2,600 | 98.04% | 2.2585 | 91,551 |

并发从 100 升到 200，**吞吐几乎不增（+0.32%），P95 却接近翻倍**。

> 流式测试定义了 **7 条严格 SSE 断言**，成功拦下 **6 个「HTTP 200 但正文为空」**的
> 响应——普通 JMeter 采样器会把它计为成功，这是流式场景典型的"假成功"。

**官网直连 vs 平台链路对照**

同一模型家族下，官网直连的 P50 / P95 / P99 分别比平台链路低约 **24% / 30% / 35%**。
报告同时标注：两边样本量不同（250 vs 1,000），**不构成严格等量 A/B 实验**，
也未将差异单方归因于平台。
